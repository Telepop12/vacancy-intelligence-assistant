# ARCHITECTURE.md — как устроена система

Vacancy Intelligence Assistant — персональный помощник по поиску работы уровня
CIO / CTO / CDTO. Документ описывает внутреннее устройство, ключевые
дизайн-решения и их причины. Команды запуска и пользовательские инструкции — в
[README.md](README.md); правила для Claude Code — в [CLAUDE.md](CLAUDE.md).

---

## 1. Целевая концепция (согласована 2026-07-04)

Система развивается от «аналитика» (ручной ввод вакансии → оценка) к
**конвейеру**, где ручной остаётся только точка принятия решения:

```
1. ПОИСК      автопоиск вакансий на hh.ru по настроенным запросам      [готово]
2. ОЦЕНКА     intake → скоринг → Career Match → рекомендация           [готово]
3. АДАПТАЦИЯ  варианты резюме под архетипы + пакет отклика             [готово]
4. ОТКЛИК     отправка пакета — вручную под сессией hh пользователя    [план: полуавтомат]
5. УЧЁТ       воронка откликов: найдено → отклик → ответ → интервью    [план]
```

Принципиальные решения по концепции:

- **Отклики никогда не уходят полностью автоматически.** Система готовит
  черновик (адаптированное CV + письмо), финальное «Отправить» — за человеком.
- **Источник вакансий №1 — hh.ru.** LinkedIn/Telegram — возможные будущие
  адаптеры intake-слоя, отдельной инфраструктуры под них не строится.
- **Пакетные операции не тратят LLM-бюджет.** Массовый триаж — только
  детерминированный rule-based скоринг; платный LLM-анализ — по явному
  действию пользователя для конкретной вакансии.

## 2. Слои системы

Четыре независимых слоя, композиция — в веб-слое (`web/app.py`):

```
agents/intake.py               нормализация вакансий (text/file/html/json/url → VacancyInput)
agents/hh_api.py               клиент hh.ru (поиск, страницы вакансий)
agents/hh_search.py            конвейер автопоиска: запросы → id → загрузка → триаж
agents/mail_radar.py           почтовый радар: рассылки LinkedIn/hh → лиды → триаж
agents/career_watch.py         обходчик карьерных страниц таргет-листа → триаж
core/                          анализ вакансии (keyword-скоринг + LLM-семантика + синтез)
agents/resume_intelligence.py  разбор резюме → ResumeProfile
agents/career_match.py         резюме × вакансия → CareerMatchResult (LLM)
web/app.py                     FastAPI: маршруты, композиция слоёв, рендеринг
```

### Поток данных основного сценария `/match`

```
from_text()/from_file()/from_url() → VacancyInput (нормализован, с intake confidence)
load_resume() + analyze_resume()   → ResumeProfile (rule-based + LLM)
analyze(vacancy, profile)          → VacancyAnalysis (keyword score, эво-потенциал, DI-слой)
career_match(...)                  → CareerMatchResult (полный карьерный анализ, LLM)
match_result.html                  → дашборд (режимы Interview / Analyst)
```

### Поток данных автопоиска `/search`

```
config/hh_search.yaml (запросы, регион, лимиты)
  → hh_api.search_vacancy_ids()      id по каждому запросу, дедупликация
  → фильтр по состоянию               output/hh_search_state.json: только новые id
  → hh_api.fetch_vacancies_batch()   полные описания, с паузами и ретраями
  → from_json() → RuleBasedAnalyzer  триаж: score + рекомендация (без LLM)
  → таблица по убыванию score        «Полный анализ» → /analyze/hh/{id} → LLM-конвейер
```

### Поток данных почтового радара `/radar` (спринт A, 2026-09-02)

Gmail MCP доступен только в сессии Claude Code — сервер сам в ящик не ходит.
Поэтому конвейер двухзвенный: сессия добывает письма, модуль их разбирает.

```
Сессия Claude (Gmail MCP)
  фильтры: from:jobalerts-noreply@linkedin.com;
           from hh.ru + тема «Подходящие вакансии для резюме:»
  → JSON [{sender, subject, date, body(plain text)}]
  → POST /radar/import  или  py -m agents.mail_radar emails.json

agents/mail_radar.py
  → parse_linkedin_body()/parse_hh_body()  → MailLead (id, название, компания…)
  → дедуп по (source, id)                   output/mail_radar_state.json
  → hh-лиды:  hh_api (JSON-LD) → register_vacancy(source="mail:hh",
              resume_variant из темы письма) → общий search state
  → LinkedIn-лиды: карточки на /radar — скрейпинг LinkedIn запрещён
              (риск бана аккаунта); текст вставляется руками, лид
              помечается converted и уходит в общий конвейер
```

Ошибочные hh-загрузки не считаются увиденными — следующий запуск повторяет их
(тот же принцип, что в автопоиске). Тема hh-письма несёт вариант резюме
(CIO/CDO/CTO) — он сохраняется в `TriageItem.resume_variant` и виден в триаже.

Актуальность LinkedIn-лидов: `py -m agents.mail_radar --check-linkedin [N]`
(с хоста — из контейнера LinkedIn недоступен, DNS-блок в РФ; VPN на Docker не
распространяется). Запрашивается ПУБЛИЧНАЯ гостевая страница вакансии без
логина и cookies аккаунта, не больше 40 за прогон, с паузами 2–5 с; маркер
`closed-job` / «Заявки на эту вакансию больше не принимаются» → лид уходит в
архив (`closed`). Первый признак блокировки (HTTP 999/403/429, authwall,
заглушка без `<h1>`) останавливает прогон — остаток проверится в следующий
раз. На странице /radar лиды старше 14 дней свёрнуты: вакансии LinkedIn
живут 2–4 недели.

### Поток данных обходчика карьерных страниц `/targets` (спринт A, 2026-09-02)

Таргет-лист — `config/target_companies.yaml` (согласован заказчиком: крупный
бизнес, группы пром/агро/химия, ИТ-интеграторы и телеком, финтех/логистика;
плюс ИТ-сателлиты холдингов — ИТ-функции часто выведены в отдельные юрлица).

```
channel=site  страница(и) вакансий → ссылки по link_pattern из HTML
              (+ JSON: __NEXT_DATA__/__INITIAL_STATE__ при json_scan, api_url)
channel=hh    JS-сайты и сайты за антиботом → один поиск hh по employer_id
  → фильтр названий title_include/title_exclude (только руководящие титулы)
  → снапшот-дифф output/career_watch/<company>.json (виденные ссылки)
  → новые: страница вакансии → intake.from_html → rule-based триаж →
    общий search state, source="career:<Компания>", id = c<sha1(url)>
```

Предохранители: паузы между запросами и компаниями, лимит новых вакансий на
компанию за прогон, лимит hh-компаний за прогон и общий кулдаун hh. Ошибка
одной страницы/компании не роняет прогон. Три сайта (Альфа-Банк, РЖД,
Металлоинвест) подписаны российским корневым CA — сертификат Минцифры лежит в
`config/certs/` и добавляется в SSL-контекст. Без LLM. Разведка страниц
(static/spa/ats/hh, антибот) выполнена субагентами 02.09 — детали в `note`
каждой компании конфига.

## 3. Ключевые дизайн-решения

### 3.1 Intake-слой обязателен

`analyze()` и `career_match()` никогда не получают сырой текст — всё проходит
через `agents/intake.py` и приходит как `VacancyInput` с нормализованным
текстом, метаданными и оценкой качества входа (HIGH/MEDIUM/LOW + причины).
Новый источник вакансий = одна функция `from_X()`; слои анализа не меняются.

### 3.2 Доступ к hh.ru — только публичные страницы

Историческая справка: в декабре 2025 hh.ru закрыл анонимный доступ к API
вакансий (HTTP 403) и прекратил поддержку API для соискателей (15.12.2025);
регистрация приложений на dev.hh.ru открыта только под задачи работодателей.

Решение: **канал — публичные HTML-страницы hh.ru**, они отдаются без
JavaScript и содержат полные структурированные данные:

- страница вакансии → блок JSON-LD `JobPosting` (название, работодатель,
  описание, локация, зарплата);
- страница поиска → id вакансий берутся ТОЛЬКО из карточек выдачи
  (`data-qa="serp-item__title"`, затем `hhtmFrom=vacancy_search_list`);
  на странице есть ещё ~30 id из блоков «похожие/рекомендованные» и JSON
  начального состояния — регулярка по всей странице тянула их в триаж
  (медицинские «вакансии дня» с нулевым баллом, 2026-09-02). Фолбэк на
  все `/vacancy/<id>` оставлен на случай смены разметки.

Код пути через официальный API (`HH_ACCESS_TOKEN`) сохранён «спящим» на случай
смены политики hh.ru, но не рекомендуется и не используется.

### 3.3 Защита от анти-бота hh.ru

Эмпирически установлено (июль 2026): анти-бот hh.ru блокирует «холодные»
запросы к `/vacancy/{id}` куда агрессивнее, чем запросы с cookies от
предыдущего визита. Поэтому:

- **единая cookie-сессия** на все запросы (`http.cookiejar` + общий opener);
  пакетная загрузка наследует cookies от шага поиска; холодный одиночный
  запрос при 403 «прогревает» сессию визитом на страницу поиска и повторяет;
- **рандомизированные паузы** 1.4–2.2 с между запросами;
- **один ретрай** после паузы ~7 с при 403/429;
- **предохранитель**: 3 блокировки подряд → пакет останавливается, остаток
  переносится на следующий запуск с понятным сообщением пользователю.

Неудачно загруженные вакансии **не** записываются в состояние как
обработанные — следующий запуск повторяет их автоматически.

### 3.4 Два скоринга параллельно (Career Match, «вариант B»)

| Score | Источник | Что оценивает |
|---|---|---|
| Keyword Score | rule-based, детерминированный | совпадение ключевых слов по 6 категориям с весами |
| Career Match Score | LLM | вся карьерная траектория + переносимые компетенции |

Смысл: ATS-подход «смотрим последнее место работы» занижает кандидатов с
эволюционирующей карьерой. LLM-скор видит скрытую релевантность
(инфраструктура → enterprise-мышление → трансформация).

### 3.5 Decision Intelligence и эволюционный потенциал

Итоговая рекомендация ≠ функция от score. `recommendation_engine.synthesize()`
может поднять вакансию с низким keyword score до «ЗАПУСТИТЬ В РАБОТУ», если
высок эволюционный потенциал (доступ к CEO/board, новое AI-направление,
измеримый ROI). Каждая рекомендация объяснима: rationale, риски, возможности,
лучший/худший сценарии, вопросы для валидации.

### 3.6 Иерархия анализаторов

```
core/analyzers/base.py        BaseAnalyzer (ABC)
  └─ rule_based.py            RuleBasedAnalyzer — keyword-скоринг, шаблоны писем
       └─ hybrid.py           HybridAnalyzer — rule-based + плейсхолдеры LLM-полей
            └─ claude_analyzer.py  ClaudeAnalyzer — совместимое имя адаптера LLM-шлюза
```

`core/analyzer.py::analyze()` использует локальную Ollama через единый шлюз;
если она недоступна, вызов мягко деградирует до `HybridAnalyzer`.
`purpose="prep"` маршрутизируется отдельно и требует `OPENAI_API_KEY`.

### 3.7 Правила работы с LLM

- Все вызовы проходят через `core/llm.py`; провайдеры реализованы в
  `core/llm_router.py`. По умолчанию используется Ollama с `qwen3.8:27b`.
  Вызовы с `purpose="prep"` уходят в OpenAI Responses API на `gpt-6-astra`.
  Модели, таймауты и маршруты меняются только в `config/llm.yaml`.
- Ollama вызывается через `/api/chat` с `format: json`, `think: false` и
  повтором при оборванном или невалидном JSON. На хосте адрес —
  `127.0.0.1:11434`, из Docker — `host.docker.internal:11434`.
- OpenAI использует Responses API, JSON mode, `reasoning.effort` и
  `store: false`. Для маршрута подготовки нужен `OPENAI_API_KEY` в `.env`.
- `core.llm.call_research()` использует hosted tool `web_search`. Шлюз
  возвращает URL из `web_search_call.action.sources` и цитат, поэтому
  вызывающий код по-прежнему отбрасывает выдуманные моделью ссылки.
- `cached_prefix` ставит резюме и факт-базу первыми в инструкции. Это
  сохраняет одинаковый порядок контекста и даёт OpenAI возможность
  автоматически кешировать повторяющийся префикс.
- Офлайн-тесты устанавливают `LLM_DISABLED=1`: они не могут случайно
  вызвать ни OpenAI, ни локальную Ollama.
- Резюме передаётся в промпт **целиком, без усечения** — усечение приводило к
  анализу только последнего места работы.
- `parse_roles_history()` извлекает позиции по датным диапазонам, промпт
  требует цитировать каждую компанию в формате «В [Компания] ([период]) …» —
  иначе модель скатывается к последней позиции.
- Все системные промпты содержат языковой блок: русский язык, запрет
  английского профжаргона (исключения: AI, ERP, MLOps, ROI, P&L, KPI, CEO,
  CIO, CTO, M&A, MBA).

### 3.8 Варианты резюме вместо «CV под вакансию» (ограничение hh.ru)

На hh.ru отклик отправляется резюме, **уже существующим в аккаунте** (новое
проходит модерацию ~10 минут) — генерировать резюме под каждую вакансию
бессмысленно. Поэтому адаптация трёхуровневая:

1. **Сопроводительное письмо** — единственный настоящий пер-вакансийный
   артефакт на hh (мгновенно, без модерации). Требования заказчика: короткое
   (~120–150 слов), структура «обо мне → почему я → заключение с следующим
   шагом», без канцелярита и ИИ-штампов. Реализовано в
   `agents/application_package.py` (`/package/hh/{id}`): письмо + выбор
   варианта резюме + карта «требование → факт» для проверки перед отправкой.
   Иерархия источников фактов: канон (мастер) → факт-база
   `data/resume/facts.md` (только статус ✅; разделы 🚫 игнорируются);
   всё, что расходится с каноном, не используется.
2. **Постоянные варианты резюме** (`agents/resume_variants.py`,
   `config/resume_variants.yaml`): 5 архетипов — CIO, CTO, CDTO, CAIO,
   универсальный. Контент генерируется из канонического резюме
   (`data/resume/`, в .gitignore — персональные данные). Железное правило в
   промпте: никакой выдумки фактов, только переакцентирование. Система
   честно указывает пробелы опыта под архетип (`honest_gaps`).
3. **Адаптированный DOCX** — для каналов вне hh (email, рекрутёры, LinkedIn).

### 3.9 Прочие соглашения

- **DOCX → Markdown** при загрузке резюме (по именам стилей абзацев):
  сохраняет структуру для LLM и позволяет рендерить в браузере через marked.js.
- **Шаблонные хелперы передаются в Jinja2 как callables** (`action_color`,
  `p_css`), вызываются в шаблоне: `{{ action_color(label) }}`.
- **Состояние — файлы в `output/`** (git-ignored, в Docker — volume):
  `registry.csv` — журнал анализов, `hh_search_state.json` — обработанные
  вакансии автопоиска. Переход на SQLite запланирован на этапе «воронка».

### 3.10 База знаний о собеседованиях в промптах подготовки («Подготовка 2.0», 2026-09-21)

Проблема: генератор подготовки опирался на общие представления модели о том,
как проходят собеседования. Собранная база `data/interview_kb/` (три файла,
~290 КБ, около 100K токенов) целиком в промпт не помещается и не нужна.

Решение — загрузчик `agents/interview_kb.py`:

- **Секции ищутся по ключевым словам заголовков** («Банк вопросов», «Паттерны
  процесса», «Что взять в генератор»), а не по номерам: квартальное обновление
  базы может перенумеровать разделы, код при этом не меняется. Разделы «Что
  взять в генератор» читаются как нумерованные списки правил —
  `rules(file, 1, 7)` возвращает нужные пункты.
- **Срезы 3–12 КБ под конкретный промпт**: банк реальных вопросов — в этап
  вопросов интервьюера; стоп-слова работодателей и ошибки кандидатов — в
  HR-этап; правила «что спросить у нанимателя» — в вопросы работодателю;
  паттерны процесса, самопрезентация, 100 дней, истории, повестка — в три
  новых этапа. Каждая выдержка начинается с «[источник: файл — раздел]».
- **Профиль процесса компании читается из самой базы**: разделы «Компании с
  найденными страницами» (page), «содержимое не получено» (blocked), «Не
  найдено» (not_found); таблица ALIASES только добавляет синонимы (Тинькофф →
  Т-Банк, СберТех → Сбер, ВымпелКом → Билайн). Короткие латинские имена
  (IBS, VK, MTS) матчатся по границе слова, иначе «ibs» находился в «Sibsoft».
  Компании нет — берётся типовой сценарий C-level, и модель прямо говорит об
  этом в блоке.
- **Источники под каждым блоком.** Модель перечисляет метки и адреса, которые
  буквально встречаются в выдержке; `_clean_sources()` отбрасывает строки без
  совпадений с выдержкой (защита от выдуманных ссылок) и разворачивает [S18]
  и «источник 8» в названия площадок из сводных таблиц базы.
- **«Чего не говорить»** — детерминированный чек-лист из 14 пунктов с
  источниками в самом модуле (`DONT_SAY`), плюс 3–5 личных пунктов от модели
  под болевые зоны кандидата.

Решения по составу пакета:

- **Восемь вызовов модели вместо четырёх** (с 22.09.2026 — Opus 5 по
  карте `models: {prep: …}` в `config/llm.yaml`, решение заказчика; все
  вызовы генератора подготовки помечены `purpose="prep"`). Новые этапы сгруппированы по
  смыслу: (4) процесс + самопрезентация + 100 дней; (5) истории и кейсы;
  (6) повестка 2026 + блиц + личные «не говорить» + пять цифр; (7) «что бы
  вы улучшили у нас» — 4–6 гипотез со стороны с опорой «вакансия / компания /
  отрасль», формулировкой вслух и проверочным вопросом (второе замечание
  приёмки 21.09: вопрос проверяет знание отрасли, компании и вакансии, а
  готовых рецептов от человека со стороны не ждут; модель обязана честно
  писать, что компания ей неизвестна, и опираться на вакансию и отрасль).
  Ошибка этапа 4–7 не роняет пакет: блок остаётся пустым, причина пишется в
  `stage_errors`, пакет сохраняется — иначе сбой на восьмом вызове терял бы
  результат семи предыдущих.
- **Истории берутся только из личного файла `data/resume/stories.md`**
  (вне git; шаблон с подсказками создаётся автоматически). В резюме и
  факт-базе нет конфликтов и провалов, а выдумывать их система не имеет права.
  Пока файл пуст, модель строит каркасы из реальных проектов резюме с явной
  пометкой «каркас из резюме» и полем «что вспомнить»; заполненный файл
  модель только шлифует под вакансию. Решение заказчика 21.09.2026.
- **Шпаргалка без модели.** `build_cheatsheet()` собирает одну страницу из
  сохранённого пакета: самопрезентация 1–3 минуты, козыри, три самых
  неудобных вопроса с отточенными ответами судьи (добор из вопросов-рисков),
  пять цифр, вопросы работодателю, этапы, блиц, три формулировки «что бы вы
  улучшили» вслух, «не говорить». Отдельная страница `/prep/{vid}/cheatsheet`
  с печатью в A4.
- **Окошко «Спросить ИИ» в разделах** (замечание приёмки 22.09). Один
  вызов `ask_in_block(package_id, block, question, vacancy_text)`: системный
  промпт задаёт роль раздела из словаря `BLOCKS` (в спарринге — раунд, в
  блице — короткий ответ, в историях — оформление рассказа кандидата без
  досочинения), пользовательский — вакансия, резюме, факт-база, сжатое
  содержимое раздела (`_block_context`, чтобы дополнять, а не повторять) и
  последние три вопроса кандидата в этом разделе для связности. Ответы
  живут в `PrepPackage.block_qa` и переживают перегенерацию только вместе с
  пакетом (перегенерация создаёт новый пакет — это осознанно: старые ответы
  привязаны к старому содержимому разделов).
- **Фоновая сборка (BACKLOG 6a, 22.09).** `agents/prep_jobs.py` держит
  задачи в памяти процесса: поток на пакет, `build_prep(progress=…)`
  отчитывается по ключам `STAGES`, страница `prep_progress.html` опрашивает
  `/prep/{vid}/status` и сама переходит к готовому пакету. Упавшая на
  обязательном этапе сборка не перезапускается при обновлении страницы —
  иначе каждое обновление стоило бы денег; перезапуск только по
  `?regenerate=true`. Досборка (`resume_prep`) пересобирает лишь
  недостающие необязательные этапы по содержимому пакета
  (`present_stages`), а не по журналу ошибок.
- **Совместимость.** Старые пакеты (`schema_version` 1) открываются как
  раньше с подсказкой перегенерировать; `_package_from_dict()` терпим к
  недостающим полям. Одна страница с закреплённым оглавлением, без вкладок
  (решение заказчика).
- Попутно исправлен редирект со старых адресов `/prep/hh/{id}` и
  `/package/hh/{id}`: он терял `?regenerate=true`, и кнопка
  «перегенерировать» молча отдавала кеш.

**Обновление 21.10.2026 по замечаниям заказчика** (`schema_version` 3):

- **«О компании» — первый раздел и этап 0.** `agents/company_research.py`
  делает один вызов с веб-поиском (до 10 поисков и 5 чтений страниц):
  справка по восьми фиксированным темам — масштаб, собственники,
  менеджмент, структура, финансы, ИТ-проекты, цифровизация и AI, закупки
  ИТ. Защита от выдумки: «не найдено» — нормальный ответ; адреса темы
  сверяются с результатами поиска (`verify_urls`: тот же адрес или тот же
  сайт), тема без подтверждения помечается; пустой поиск даёт
  предупреждение на всю справку. `digest()` (до 3500 знаков, без тем «не
  найдено») уходит в вопросы интервьюера, вопросы работодателю, рассказ о
  себе и 100 дней, структуру и персонал, «что бы вы улучшили». Ресёрч не
  обязателен: при сбое этапы получают «справка не собрана» и опираются на
  вакансию.
- **Архив компаний** (`output/companies/`, вне git): веб-поиск платный, а
  пакеты по одной компании пересобираются часто. `get_company_profile()`
  сначала ищет запись по ключу компании (бренд из кавычек без
  организационно-правовой формы: «Сеть клиник «СМ-Клиника»» и «ООО
  «СМ-Клиника»» дают «см клиника»; бренды из найденного юрлица
  добавляются как синонимы) и идёт в поиск, только если записи нет или она
  старше 183 дней. Пустые и неподтверждённые справки в архив не кладутся.
  Кнопка «Обновить ресёрч» (`POST /prep/{vid}/company/refresh`) ищет мимо
  архива и обновляет запись и раздел, не трогая остальные.
- **Сняты «Как проходит процесс» и «Козыри и риски»** — получались
  типовыми. Козыри и болевые зоны по-прежнему считаются на этапе вопросов
  интервьюера: ими питаются спарринг, вопросы работодателю и «не говорить».
  Профили процессов компаний в `interview_kb.py` остаются библиотекой.
- **Рассказ о себе — одна версия на 3 минуты** из трёх частей (кто я; опыт,
  образование, достижения; что ищу). «Что ищу» опирается на траекторию из
  резюме и `target_roles` из `config/candidate_profile.yaml`; личных мотивов
  модель не придумывает. Из HR-этапа убраны «расскажите о себе», стиль
  управления и кейсы про подчинённых — у них теперь свои разделы.
- **«Моё понимание + мой опыт».** Общее правило `_UNDERSTANDING_RULE` в
  промптах вопросов интервьюера, HR, спарринга (судья вычёркивает натяжки),
  структуры и персонала, двойника и окошек «Спросить ИИ». У `PrepQA` поля
  `understanding` и `lead` («опыт» | «понимание»); страница и `.md`
  показывают части в порядке подачи (`answer_parts`). Причина — замечание
  заказчика: модель притягивала опыт к вопросам, где его нет, а интервьюеры
  хотят слышать понимание.
- **«Структура и персонал»** — новый этап: оценка ИТ-структуры под вакансию
  (направления, численность, штат или аутсорс — с пометкой «оценка»),
  вопросы «структура и команда» и «управление подчинёнными». Выдержка базы
  `kb.team_rules()`: «руками / делегирую / контролирую», референсы у
  бывших подчинённых, ассессмент, красные флаги.
- **Параллельные этапы.** Пять необязательных этапов после обязательных
  независимы (каждый пишет свои поля) и идут в пуле из трёх потоков
  (`PARALLEL_STAGES`); `stage_errors` сортируются в порядке плана. Без
  этого десять этапов на Opus тянулись бы полчаса. «Что бы вы улучшили»
  больше не читает план 100 дней — иначе ждал бы его.
- **Совместимость.** Пакеты схемы 2 открываются: снятые разделы просто не
  показываются, старая самопрезентация видна с пометкой; кнопка
  «дособрать» добавляет «О компании» и «Структуру и персонал» без
  пересборки остального.

### 3.11 Отбор внешних практик для «Что улучшить» (2026-10-29)

`agents/practice_research.py` получает требования вакансии и полный
доступный контекст «О компании» (подтверждённые разделы, без усечения
сводкой на 3500 символов). Поиск формируется под их пересечение.
Резюме в поиск не передаётся: опыт кандидата ограничивает утверждения
о собственных внедрениях, но не список полезных гипотез.

Для практики нужны процесс, применение, метрика, ограничения, объяснение
применимости и дословные цитаты из вакансии и справки. Код проверяет
наличие этих опор и точное совпадение URL с результатами web search.
Совпадение домена недостаточно. Это проверка происхождения, не
автоматическое доказательство семантической корректности источника.

Принятые практики передаются в финальный `_stage_improve`. Тренды
форматируются из их конкретных полей; отраслевые гипотезы без ссылки
на принятую практику отбрасываются. Основания и ссылки сохраняются в
JSON, Markdown и показываются на странице. Старые пакеты без этих полей
по-прежнему читаются. При сбое поиска остаются вопросы по вакансии
и компании с явной пометкой; неподтверждённые тренды не подставляются.

Кеш `output/practice_research/` живёт 14 дней и привязан к версии промпта,
провайдеру, модели, вакансии и фактам компании. Пустой поиск не кешируется.
Офлайн-тесты изолируют этот каталог во временной папке.

### 3.12 Составные вопросы кандидата (2026-10-29)

`_COMPOUND_ANSWER_RULE` добавлен после `_UNDERSTANDING_RULE` в инструкции
`_ASK_SYSTEM` и `_BLOCK_SYSTEM`. Для сложного вопроса он снимает ограничение
понимания несколькими предложениями и задаёт порядок от бизнеса и отрасли
к проектам, метрикам и проверкам. Простые вопросы остаются короткими.

Пример бюджетного вопроса разделяет достаточность и обоснованность суммы,
эффективность расходов, внутреннюю структуру затрат и рыночность стоимости.
Ресурсный разрез (персонал, оборудование, ПО, услуги) не суммируется с
разрезом по назначению (эксплуатация, развитие). Доля ФОТ не получает
автоматический вердикт без учёта внешнего труда и результатов. Сопоставления
требуют одинакового периода и состава затрат; численные отраслевые нормы
допустимы только из имеющихся источников. R&D учитывается отдельно.
Оба вида свободных вопросов получают сводку «О компании» с годами.

В мини-кейсе уточнения или существенные допущения идут перед вычислениями
в произносимом ответе; note хранит дополнительные пробелы и ссылки.
Числовая опора ведёт к выводу или действию; факты, вычисления и сценарные
допущения отделяются друг от друга.

Путь справочных чисел: `data/interview_kb/benchmarks.yaml` →
`interview_kb.quantitative_context(question, company/vacancy context)` →
`_ASK_USER` / `_BLOCK_USER` → один существующий вызов LLM → сохранение пакета.
Отбор детерминирован, по теме вопроса; отраслевая карточка требует подходящего
контекста. Код проверяет обязательные метаданные, дату ручной проверки и срок
пересмотра. Карточка передаётся целиком, чтобы не отрезать URL или оговорки.
Это не проверка истинности статистики: источники проверяются человеком при
обновлении справочника. Отсутствующий, повреждённый или просроченный справочник
не блокирует ответ: остаются данные условия и явно обозначенные расчёты.

Схемы сохранения не менялись. Структура ответа — обычный текст с нумерованными
заголовками и пустыми строками внутри JSON-поля. Существующий `white-space:
pre-line` в шаблоне сохраняет переносы; Jinja продолжает экранировать HTML.
Новые инструкции действуют со следующего вопроса, старые ответы не пересоздаются.

## 4. Веб-слой

FastAPI + Jinja2, серверный рендеринг, без SPA. Маршруты:

| Маршрут | Что делает |
|---|---|
| `GET /` | главная, карточки сервисов |
| `GET /vacancy` → `POST /analyze` | анализ вакансии (текст/файл/URL) |
| `GET /search` → `POST /search/run` | автопоиск hh.ru + триаж |
| `GET /radar` | почтовый радар: hh из рассылок (оценено) + LinkedIn-лиды |
| `POST /radar/import` | приём писем из сессии Claude (JSON) → ingest_emails |
| `POST /radar/lead/{key}/hide` / `restore` | скрыть/вернуть LinkedIn-лид |
| `GET /targets` → `POST /targets/run` | таргет-лист компаний: обход карьерных страниц + вакансии с них |
| `GET /analyze/hh/{id}` | полный анализ вакансии hh.ru из таблицы поиска |
| `GET /package/{vid}` | пакет отклика (письмо, вариант резюме, ИИ-скринер); `?regenerate=true` — заново |
| `GET /prep/{vid}` → `POST /prep/{vid}/ask` | пакет подготовки к интервью (10 этапов); вопрос двойнику |
| `POST /prep/{vid}/ask/{block}`, `…/delete` | вопрос к ИИ внутри раздела пакета (12 разделов, `BLOCKS`; в «О компании» — с веб-поиском); ответ сохраняется под разделом |
| `GET /prep/{vid}/cheatsheet` | шпаргалка «10 минут до звонка» из сохранённого пакета, без модели |
| `GET /prep/{vid}/status`, `POST /prep/{vid}/resume` | JSON-прогресс фоновой сборки; досборка упавших необязательных этапов (`agents/prep_jobs.py`) |
| `POST /prep/{vid}/company/refresh` | свежий ресёрч компании мимо архива; обновляет архив и раздел «О компании» |
| `GET /resume` → `POST /resume/analyze` | Resume Intelligence |
| `GET /match` → `POST /match/analyze` | Career Match (вакансия × резюме) |
| `GET /output/{filename}` | выдача сгенерированных отчётов |
| `GET /health` | health check (используется Docker healthcheck) |

Развёртывание: локально `uvicorn web.app:app`, либо Docker
(`docker compose up --build -d`) — образ `python:3.11-slim`, `output/`
примонтирован с хоста, `.env` пробрасывается, `restart: unless-stopped`.

## 6. Известные ограничения

- Парсинг hh.ru зависит от вёрстки публичных страниц (JSON-LD) — при смене
  разметки потребуется правка `hh_api.py`; тесты на фикстурах это поймают.
- Пакетная загрузка намеренно медленная (паузы) — ~1–2 минуты на 30 вакансий.
- Вакансии без блока JobPosting (архивные/скрытые) не триажируются и
  переспрашиваются при каждом запуске — известный компромисс.
- `POST /search/run` и пакет отклика выполняются синхронно в запросе; при
  росте объёмов перейдём на фоновую задачу с прогрессом — механизм уже есть
  у пакета подготовки (`agents/prep_jobs.py`, 22.09.2026).
