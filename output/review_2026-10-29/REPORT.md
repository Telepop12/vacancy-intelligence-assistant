## Главный результат

Портал и детерминированный анализ работают. Полную работоспособность AI-функций подтвердить нельзя: **обе настроенные модели Anthropic возвращают HTTP 403 `verification_required`**. Штатные офлайн-тесты проходят, но пять дополнительных регрессионных проверок выявили ошибки, которые они не покрывают.

## Блокер эксплуатации: Anthropic требует верификацию организации

Два коротких реальных запроса выполнены из работающего контейнера через `core.llm.call_json`: к общей модели `claude-sonnet-5` и модели подготовки `claude-opus-5-5`. Ключ настроен. Оба запроса получили `PermissionDeniedError`, HTTP 403, `error_code=verification_required`.

Ответ провайдера: организация сейчас не может получать ответы Claude; администратору нужно выполнить действия в [Anthropic Verification Portal](https://portal.anthropic.com/verify). Это ответ внешнего сервиса, а не предположение по конфигурации. Ключ и личные данные кандидата в проверках не выводились; в запросах использовалось только требование вернуть маленький JSON.

Последствия: LLM-анализ вакансий откатывается к заглушкам; новые пакеты отклика, подготовка к интервью и веб-ресёрч не могут полноценно генерироваться. Сохранённые материалы продолжают открываться. После решения вопроса с верификацией нужно повторить живые проверки; этого результата недостаточно для подтверждения всего AI-конвейера.

## Замечания к коду

### 1. P1 — поиск затирает изменения реестра, сделанные во время загрузки вакансий

**Место:** `agents/hh_search.py:207`, `:218`, `:245`; запись отдельной вакансии — `:155`.

`run_search()` читает общий JSON-реестр до сетевой загрузки, а после неё записывает старый снимок целиком. За время загрузки пользователь может добавить вакансию или другой источник может зарегистрировать её через `register_vacancy()`. Такая запись исчезает из реестра при завершении поиска. Аналогично могут теряться удаления и изменения существующих записей. Фоновый монитор и ручные действия делают этот сценарий возможным даже при одном пользователе.

**Воспроизведено:** во время замоканной загрузки зарегистрирована `m-review`; до завершения поиска реестр содержит эту запись, после завершения — только `12345`. Файл самой ручной вакансии может остаться, но она пропадает из общего списка поиска.

**Исправление:** выполнять короткие операции чтения/обновления/сохранения общего состояния под одной синхронизацией; сетевую загрузку вынести за неё. Сливать результаты с актуальным состоянием, учитывая удаления. Одной атомарной замены файла недостаточно для предотвращения потери обновлений. Для нескольких процессов понадобится межпроцессная блокировка или транзакционная БД.

### 2. P2 — скачивание допускает выход в соседний каталог с тем же префиксом

**Место:** `web/app.py:937–946`, условие `:941`.

Проверка `str(path).startswith(str(OUTPUT_DIR.resolve()))` сравнивает строки, а не принадлежность каталогу. Каталог `output_private` проходит проверку для разрешённого `output`.

**Воспроизведено:** во временной папке создан только синтетический `output_private/private.json`; запрос `/output/%2e%2e/output_private/private.json` через настоящий FastAPI-маршрут вернул HTTP 200 и его содержимое. Пользовательские файлы для проверки не читались.

**Границы:** обход позволяет читать существующие файлы с разрешёнными расширениями `.md`, `.json`, `.docx` в путях, которые проходят строковый префикс. Это не произвольное чтение любого файла диска.

**Исправление:** после `resolve()` проверять `path.is_relative_to(OUTPUT_DIR.resolve())` и `path.is_file()`.

### 3. P2 — выдуманная страница считается подтверждённым источником

**Место:** `agents/company_research.py:215–229`, особенно `:227`; признак подтверждения — `:264`. Это относится к новым staged-изменениям.

`verify_urls()` принимает любой адрес на домене, который хотя бы один раз появился в поиске. Результат поиска с `/id/1` разрешает ссылку на `/id/999999999999999999`, которая не была найдена и может относиться к другой компании или не существовать. Затем `build_profile()` устанавливает `verified=True`; такая справка может попасть в архив на 183 дня и в контекст других этапов подготовки.

**Воспроизведено:** поиск вернул только `https://www.rusprofile.ru/id/1`; выдуманный адрес на том же домене принят, финансовая секция помечена подтверждённой. Текущий `qa/test_company_research.py` прямо ожидает принятие другого `/id/999`, то есть закрепляет ошибочную семантику.

**Исправление:** принимать точное совпадение нормализованной страницы или отдельно подтверждённый результат перенаправления. Совпадение одного домена не подтверждает страницу. Это исправление проверяет происхождение ссылки; проверка того, что источник действительно подтверждает текст утверждения, остаётся отдельной задачей.

### 4. P2 — две ручные вакансии за секунду получают один ID

**Место:** `agents/vacancy_store.py:36–37`, `:45–50`.

`new_manual_id()` использует время с точностью до секунды. Два добавления без числового hh-ID — например, быстрый повтор запроса или две вкладки — получают одинаковое имя файла; вторая вакансия молча заменяет первую. Связанные пакеты также привязываются к одному ID.

**Воспроизведено:** при фиксированной секунде два сохранения вернули один ID и оставили единственный JSON со второй вакансией.

**Исправление:** UUID/случайный суффикс и защита от перезаписи при создании. Микросекунды уменьшают риск, но эксклюзивное создание или уникальный идентификатор надёжнее.

### 5. P2 — два анализа за секунду перезаписывают отчёты

**Место:** `core/report.py:85–86`, `:121–122`.

И JSON, и Markdown названы `analysis_YYYYMMDD_HHMMSS`. Два анализа за одну секунду создают одну пару файлов, хотя в CSV появляются две записи. Ссылка на первый отчёт после второго запроса фактически отдаёт второй.

**Воспроизведено:** два последовательных POST `/analyze` в изолированном TestClient дали две строки CSV и один JSON. Дополнительный регрессионный тест с фиксированной секундой подтверждает одинаковый путь для разных анализов.

**Исправление:** присваивать анализу уникальный ID один раз и использовать его в именах обоих файлов; не генерировать разные случайные ID отдельно для Markdown и JSON.

### 6. P2 — часть штатного pytest пишет в пользовательский output

**Место:** `qa/test_vacancy_analysis.py:54`, `qa/run_functional_tests.py:29–30`, `:66–73`, `:185–199`; в `qa/conftest.py` нет общей изоляции этих путей.

Pytest оборачивает старые функции, которые запускают `main.py` без временного `--output`. Даже тесты с `--no-registry` создают настоящие отчёты, а `test_registry_updated` добавляет строку в настоящий `output/registry.csv`. В Docker это тот же примонтированный пользовательский каталог.

**Подтверждено двумя прогонами:** создано 12 файлов отчётов и две строки с `sample_vacancy.txt`. После обнаружения я удалил только две точно идентифицированные синтетические строки, сохранив остальной CSV побайтно; 12 файлов перенёс в папку этого ревью. Реестр после очистки содержит 179 строк данных. Журнал уборки — `cleanup.json`, тестовые отчёты — `test_outputs/`.

**Исправление:** передавать каждому CLI-подпроцессу `--output tmp_path`, а проверку реестра направлять в тот же временный каталог. Перенаправить также константы старого runner, которыми он читает результат. Одного monkeypatch родительского процесса недостаточно для CLI-подпроцессов.

### Дополнительно: P3 — smoke-тест главной страницы устарел

`web/smoke_test.py:85` требует слово «Проанализировать» на `/`, хотя текущая главная страница является навигационной, а форма находится на `/vacancy`. Главная отвечает HTTP 200, но это условие ложно. Полный старый smoke-скрипт не запускался: его валидные POST пишут в рабочий реестр и вызывают настроенную модель. Вместо него выполнены отдельные HTTP-проверки и изолированные POST.

## Ограничения и порядок исправления

Визуальная проверка в браузере не выполнена: инструмент автоматизации не смог запустить свою среду из-за ошибки Windows sandbox. HTTP и серверный рендеринг проверены отдельно. Полный живой AI-конвейер, реальный поиск hh, обход карьерных сайтов и доставка Telegram в этом ревью не проверялись. Сборка образа заново не запускалась; проверен уже работающий образ. Восемь штатных живых LLM-тестов исключены, потому что реальные короткие запросы подтвердили блокировку провайдера.

Сначала устранить внешнюю блокировку Anthropic и потерю обновлений общего реестра. Затем закрыть выход за каталог и ошибочное подтверждение источников, обеспечить уникальность ID и отчётов, изолировать pytest от пользовательских данных и обновить smoke-тест. После исправлений повторить пять регрессий и живую генерацию на одной тестовой вакансии.
